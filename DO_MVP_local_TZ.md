# DO --- краткое ТЗ MVP

**Цель:** за один вечер создать локально работающий веб-трекер задач для
двух пользователей --- меня и Дианы. На первом этапе приложение
запускается только на компьютере разработчика; сервер, домен, HTTPS и
публичный доступ не настраиваются.

## 1. Продукт

Минималистичный таск-трекер: быстро добавить задачу, увидеть список,
назначить категорию и ответственного, отметить выполнение.

**Основной UX:** минимум действий, удобная работа с телефона и
компьютера, без перегруженных экранов.

## 2. Функции MVP

Обязательно: - Создание, просмотр, редактирование и удаление задач. -
Быстрое добавление задачи по названию. - Статусы: `ACTIVE`,
`COMPLETED`. - Категории: `Дом`, `Работа`, `Личное`. - Приоритеты:
`Обычный`, `Высокий`. - Необязательный срок выполнения. - Ответственный:
я, Диана или без назначения (общая задача). - Фильтры: все / активные /
выполненные; по категории и ответственному. - Поиск по названию. -
Данные сохраняются в PostgreSQL и остаются после перезапуска приложения.

Не входит в MVP: AI, Telegram, уведомления, повторяющиеся задачи,
вложения, аналитика, мобильное приложение, сложные роли и права.

## 3. Технологии

-   **Frontend:** React + TypeScript + Vite.
-   **UI:** Tailwind CSS + Lucide Icons.
-   **Backend:** Kotlin + Ktor, REST API.
-   **БД:** PostgreSQL.
-   **Миграции:** Flyway.
-   **Доступ к БД:** Exposed или JDBC; выбрать один подход и не
    усложнять.
-   **Локальный запуск:** Docker Compose.

## 4. Данные

Минимальная модель:

-   `users`: `id`, `name`, `email`, `password_hash`, `created_at`.
-   `workspaces`: `id`, `name`, `created_at`.
-   `workspace_members`: `workspace_id`, `user_id`, `role`.
-   `categories`: `id`, `workspace_id`, `name`, `color`.
-   `tasks`: `id`, `workspace_id`, `created_by`, `assignee_id`
    (nullable), `category_id` (nullable), `title`, `description`
    (nullable), `status`, `priority`, `due_date` (nullable),
    `created_at`, `updated_at`, `completed_at` (nullable).

Одно общее семейное пространство с двумя участниками.
`assignee_id = NULL` означает общую задачу. Категории создаются при
первичной инициализации.

Все запросы к задачам должны ограничиваться пространством, участником
которого является текущий пользователь.

## 5. API

Префикс: `/api`.

-   `POST /auth/login`
-   `POST /auth/logout`
-   `GET /auth/me`
-   `GET /tasks` --- фильтры `status`, `categoryId`, `assigneeId`, `q`.
-   `POST /tasks`
-   `GET /tasks/{id}`
-   `PATCH /tasks/{id}`
-   `DELETE /tasks/{id}`
-   `PATCH /tasks/{id}/complete`
-   `PATCH /tasks/{id}/reopen`
-   `GET /categories`
-   `GET /workspace`
-   `GET /workspace/members`
-   `GET /health`

Использовать единый формат JSON-ответов и ошибок. Проверять входные
данные и права доступа на backend. Пароли хранить только в виде стойкого
хеша. Для браузерной авторизации использовать серверную сессию в
HttpOnly cookie; предусмотреть CSRF-защиту.

Для локального MVP допустима предварительная инициализация двух тестовых
пользователей. Публичную регистрацию не делать.

## 6. Интерфейс

Главный экран: - Заголовок `do.` и приветствие. - Счётчики активных и
выполненных задач. - Поле быстрого добавления. - Список задач с
чекбоксом, названием, категорией, приоритетом, сроком и ответственным. -
Фильтры и поиск. - Действия редактирования и удаления. - Отдельное
отображение выполненных задач.

Требования: - Адаптивная вёрстка для мобильного и десктопа. - Enter
добавляет задачу, после добавления поле очищается. - Понятные состояния
загрузки, ошибки и пустого списка. - Подтверждение удаления. - Не делать
сложные анимации и лишние экраны.

## 7. Локальная архитектура и запуск

``` text
Browser
  |
  v
Vite / React (localhost:5173)
  |
  | /api через dev proxy
  v
Ktor (localhost:8080)
  |
  v
PostgreSQL (localhost:5432)
```

Структура проекта:

``` text
do/
├── backend/
├── frontend/
├── compose.yaml
├── .env.example
├── .gitignore
└── README.md
```

Локально через Docker Compose запускать PostgreSQL и Ktor; frontend
запускать через Vite. Допускается запуск всех компонентов через Compose,
если это упрощает повторяемость.

Требования: - PostgreSQL хранит данные в Docker volume. - Секреты и
пароли находятся в `.env`, не коммитятся в Git. - Порты доступны только
на localhost. - Добавить healthcheck БД и endpoint `/api/health`. -
Миграции Flyway выполняются автоматически при старте backend. - В README
описать prerequisites, настройку `.env`, запуск, остановку и сброс
локальной БД.

Пример команд (точные команды зафиксировать в README):

``` bash
docker compose up -d db
# запустить backend и frontend согласно README
```

## 8. Критерии готовности

-   [ ] Проект запускается локально по инструкции из README.
-   [ ] Открывается веб-интерфейс.
-   [ ] Два тестовых пользователя могут войти.
-   [ ] Можно создать личную и общую задачу.
-   [ ] Можно назначить задачу себе или второму участнику.
-   [ ] Работают создание, редактирование, удаление и завершение задач.
-   [ ] Работают категории, приоритет, срок, поиск и фильтры.
-   [ ] Данные сохраняются после обновления страницы и перезапуска
    контейнеров.
-   [ ] Пользователь не может получить задачи другого workspace.
-   [ ] Нет секретов в Git; БД не доступна извне.

## 9. Порядок реализации

1.  Создать структуру репозитория и локальное окружение.
2.  Поднять PostgreSQL и проверить подключение.
3.  Создать Ktor-приложение, Flyway-миграции и `/api/health`.
4.  Реализовать пользователей, workspace и API задач.
5.  Создать React-интерфейс и подключить API.
6.  Добавить тестовые данные для двух пользователей.
7.  Проверить все критерии готовности и обновить README.

**Ограничение по объёму:** сначала реализовать сквозной сценарий
«открыть сайт → добавить задачу → сохранить в PostgreSQL → увидеть после
перезагрузки». Не добавлять функции сверх этого ТЗ до рабочего MVP.
